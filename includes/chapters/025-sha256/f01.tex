  \begin{minipage}{\linewidth}
    \small
    \begin{enumerate}
      \setlength{\itemsep}{0pt}
            \setlength{\parsep}{0pt}
      \item The stop at \texttt{schedule\_done} follows the last store. The next instruction will set \texttt{v0} to zero before return.
      \item \texttt{t0 = 0x100111e0} points past all 256 schedule bytes; \texttt{t1 = 0} marks completed expansion.
      \item The input starts \texttt{61 62 63 80}: the three \texttt{abc} octets and the padding marker. Decoding these four bytes most significant first gives numeric \texttt{W0 = 0x61626380}.
      \item The final source row ends with \texttt{00 00 00 00 00 00 00 18}. This is the original twenty-four-bit message length, serialized most significant byte first; the padding bytes are not counted.
      \item Memory stores \texttt{W0} as \texttt{80 63 62 61}: the same numeric \texttt{0x61626380}, stored low byte first. This is CPU word storage, not a second message encoding.
      \item The upper row ends with \texttt{W15 = 0x00000018}. The next row holds \texttt{W16..W19}: \texttt{61626380}, \texttt{000f0000}, \texttt{7da86405}, \texttt{600003c6}, each stored low byte first.
      \item The final four words are \texttt{W60..W63}. The next row retains \texttt{a5} outside the logical array. The independent store history rejects even same-value writes into this suffix.
    \end{enumerate}
