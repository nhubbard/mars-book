\section{Check an interface after observing its construction}
The guided checks stop before the named checkpoint instruction and compare the state
explained in that step. Later regions can remain unfinished, and completing them does
not prevent revisiting an earlier observation. A checkpoint can legitimately own an
open file descriptor: closing it is work for a later region. Completed file checks
instead run through the return and require every acquired descriptor to be closed.

Run a guided check from the chapter package with
\texttt{java -jar /path/to/cli.jar grade}, then name
\path{checks/construction/s34.kts} and your working assembly file. That example checks
the imported kernel call; choose the file matching the current step. The check supplies
its own input bytes and in-memory file fixtures. Preparing an observation file is useful
for manual debugging, but the guided check does not require a separate preparation run.

Use the seven completed-interface checks after finishing the relevant routine. A
returned development status four fails a completed-interface check. Preserve the
supplied caller and data labels for invocation; a free-writing implementation may use
different private registers, frames and algorithms. The checks require the published
results, memory intervals and failure behavior. They do not compare your source with
an instructor's instruction sequence.

For example, run \path{checks/files.kts} against the working source to exercise forced
short transfers without opening host files. Keep the real-file playback observation
separate. Public feedback covers selected cases; an instructor may grade additional
inputs that satisfy the same stated contract. An equivalent block or direct filter
must produce the same exact Q15 samples, including at rounding and clipping boundaries.
