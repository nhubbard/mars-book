Learn supplies four predictions, three Debug activities, an ordinary Run and an
independent program. This chapter explains the observations and adds deliberate
fault investigations. The final display is only the latest mask. Your task is
to explain how many stores occurred, why those stores had the required values,
and why an empty range performs none.

\section{Keep the source and execution together}

Answer the predictions through their inline choices in Learn. Its source pointer
identifies the operation under discussion. During Debug, use the debugger's
execution highlight to decide which operation is next: the lesson may already
be pointing to a later observation after recognizing the current pause.

The guided activities open three files with the same instructions and different
input words. Keep those supplied files unchanged while following the observations.
Stop one Debug session before launching the next, and check the launch's source
file if you reuse a saved configuration. Opening a different file does not change
the source of a configuration that already names a file.

\section{Predict before the first store}

Start with the default inputs, first index zero and count sixteen. Break at
\texttt{loop}. Record the current table address, next index and remaining count.
Before stepping, decide whether \texttt{beqzc} will take its branch. State the next
instruction on that path, rather than saying only that the condition is false.

For a nonzero count, the next instruction is \texttt{nop}, followed by the byte
load. Step through them and inspect \texttt{\$t3}. It should contain
\texttt{0x3F}. Explain how that mask lights the six outside bars while leaving the
middle bar and decimal point off. It is a mask selected by index zero, not the
numerical value zero sent directly to the device.

At \texttt{port\_write}, the store has not executed. Step once to
\texttt{displayed}. The device has received the mask, but the index and count
have not yet changed. Use these two pauses to distinguish a prepared transaction
from a completed one.

\section{Follow one complete iteration}

Step through the three updates and stop at \texttt{iteration\_done}. The table
address has advanced one byte, the next index is one, and the remaining count is
fifteen. Explain why the pointer update uses a 64-bit addition while these small
counts fit the word additions.

Step over \texttt{bc}. Its next instruction is at \texttt{loop}; there is no delay
slot to execute first. At the second table load, predict mask \texttt{0x06}.
Check that the port address remains unchanged. The input words and table should
also remain unchanged: this loop keeps its changing state in registers.

Write a trace for two iterations with three distinct boundaries: before the
store, after the store, and after the updates. Avoid calling the post-update index
the digit already displayed. At that boundary it names the next entry.

\section{Exercise the taken path}

Use the supplied \texttt{ranges/empty.asm}, whose inputs are first index sixteen
and count zero. Start Debug from the beginning so setup reads that file's data. At \texttt{loop}, predict a taken branch
to \texttt{done}. The following \texttt{nop} should be skipped, along with the
load and store. A one-past-table pointer is computed but not read through.

After the guided activity, use a working copy to check a second empty range with
first index zero. Its pointer differs, while the required output history is
still empty. This distinguishes the rule ``count zero
means no work'' from a special case that stops only at index sixteen.

For the next guided activity, use \texttt{ranges/tail.asm}, with first index fourteen and count two. Predict the masks for E and F,
then trace the count from two to one to zero. The index sixteen at termination
is an exclusive boundary; loading glyph sixteen would go beyond the table.

\section{Investigate one fault at a time}

In a working copy, change the pointer increment from one to two. Start with a
short range that should select adjacent entries. Predict the new load addresses
and compare them with the selected table bytes. Restore the increment afterward.
A wrong address stride can produce recognizable glyphs while violating the
requested sequence.

In another copy, remove the count decrement. Run with a bounded check or stop the
Debug session after observing repeated iterations. The count remains nonzero,
so the backward branch cannot make the top test succeed. Explain which part of
the invariant has stopped being maintained. Restore the original source before
trying the next change.

For the forbidden-slot experiment, replace the \texttt{nop} immediately after
\texttt{beqzc} with \texttt{bc done}. With a nonzero count, the conditional branch
is not taken and the next control-transfer instruction is illegal in that slot.
With count zero, the first branch jumps away before that slot executes. Predict
both outcomes, then test separate runs. A label between the instructions would
not repair the nonzero path. Restore the safe \texttt{nop} afterward.

\section{Check the output protocol}

The independent activity's ten public cases observe actual device stores,
including their byte width, destination and order. They also reject writes to
the protected table and input block, including a temporary write restored before
exit. A final F-shaped display cannot establish that all sixteen
requested writes occurred. Repeated mask values also require repeated stores:
writing the same value twice can represent two distinct requested entries.

The checks do not certify the timing of visible repaints. A rapid Run may show
only its last mask. Debug supplies useful observation boundaries, while the
execution trace supplies evidence about the whole sequence. Neither replaces
your explanation of the loop's state and stopping argument.

\section{Implement an end-pointer version}

Write the alternative from the main book using a current pointer and an exclusive
end pointer. Plan both addresses for an empty range before writing its branch.
List the register values that change and those that remain fixed. Keep the branch
comparison before the first load and keep its forbidden slot safe.

Open \texttt{independent/end-pointer.asm}. Its exit-only starter is intentionally
incomplete. Read the adjacent \texttt{README.md} for the input layout and the
public case profile. At the start of each case, a fresh simulator receives a
sixteen-byte glyph table and the supplied first-index and count words. Your
program must read those inputs and preserve the complete 32-byte block, including
its guard words. Use the supplied input interface rather than replacing it with
a fixed table and count.

The admitted ranges satisfy $0 \leq \mathit{first} \leq 16$ and
$0 \leq \mathit{count} \leq 16-\mathit{first}$. Handling invalid ranges is outside
this exercise's stated contract. The public cases include empty, single-entry,
full and tail ranges, repeated masks and an alternative glyph table. Repeated
bytes still require repeated stores: equal values can belong to distinct entries.

For a nonempty range, the read observer permits accesses within the sixteen-byte
glyph table; it does not require one particular load instruction or forbid
repeated reads within that table. For an empty range, it permits no glyph reads.
A read into the following guard is outside the permitted interval. The store
observer compares the byte transactions at the right display port and rejects
other writes within its observed device region. These are stated observation
regions, not a proof that no unrelated memory address was ever accessed.

Select Check this program in Learn. Checking assembles the current editor text,
including unsaved changes, and executes each case in a separate machine. It does
not overwrite your active Run or Debug state. The exit-only starter passes the
three empty cases and fails the seven nonempty cases. Read the first failing
case's expected and actual evidence before changing the program; a nonzero
number of passed cases is not completion of the task.

An equivalent correct implementation can use different registers, labels and
updates while producing the same ordered port writes and preserving the protected
data. The behavior checks alone cannot establish that you used an end-pointer
algorithm. Explain how you computed the exclusive end, why the test precedes the
load, and why advancing by one byte reaches that end after exactly the requested
number of entries. Instructor settings may control prerequisites, attempts and
hint release; requesting a hint does not satisfy an execution check.
